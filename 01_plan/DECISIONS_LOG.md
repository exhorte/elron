## Décisions techniques

| ID | Décision | Pourquoi | Conséquence |
|---|---|---|---|
| D-001 | **Monolithe modulaire** : Next.js 16 (App Router) + TypeScript + PostgreSQL 16. Pas de microservices, broker, base vectorielle, multi-agents, ni FastAPI. | Une seule langue côté serveur, un seul déploiement, tests simples. Aucune fonction du MVP ne justifie Python/FastAPI. | Le domaine pur (`src/domain`) est isolé de Next : extractible plus tard sans réécriture. |
| D-002 | **Racine Git = `C:\Dev\elron`**, code applicatif dans `04_code/`. Documents répartis dans les dossiers numérotés **déjà présents** : `01_plan` (plan, architecture, décisions), `02_context` (sources, catalogue, benchmark), `03_session-memory` (état, prochaines étapes), `05_project_monitoring` (tests). `CLAUDE.md` à la racine indexe le tout. | Les dossiers existaient, vides, avec ces noms. *Hypothèse sur l'intention du porteur* : déplacement trivial si autre usage voulu. | À chaque session : lire `CLAUDE.md` puis `03_session-memory/PROJECT_STATE.md`. |
| D-003 | **Drizzle ORM + migrations SQL** (`drizzle/`), pilote `pg`. PostgreSQL local via Docker Compose (projet `alx`, port **5433**). | Schéma TypeScript typé, migrations SQL lisibles et éditables (triggers, index partiels). Prisma écarté : génération de client en plus. Le projet Compose est nommé `alx` : un autre projet de la machine utilisait déjà le nom `04_code`. | `npm run db:up`, `db:migrate`. |
| D-004 | **Authentification maison** : mots de passe `scrypt` (Node natif), sessions en base (jeton aléatoire 256 bits, empreinte SHA-256 stockée), cookie HttpOnly + SameSite=Lax, contrôle d'origine sur les écritures, verrouillage après 5 échecs (15 min), hash factice anti-énumération. | Supabase Auth/Auth.js imposent un service ou une dépendance de plus et des comptes externes à créer (intervention humaine) ; le besoin MVP (e-mail + mot de passe) tient en ~100 lignes testées. | **Manque** : réinitialisation de mot de passe, vérification e-mail/téléphone (OTP), OAuth, limitation de débit par IP. Voir NEXT_STEPS. |
| D-005 | **Tables différées** : `organizations`, `organization_members`, `carrier_profiles`, `driver_profiles`, `relay_points`, `quotes`, `payments`, `payouts`, `refunds`, `disputes`, `reviews`, `notifications`. Créées : `users, sessions, traveler_profiles, cities, routes, capacity_offers, shipment_requests, bookings, shipments, shipment_items, shipment_events, audit_logs`. | « Ne crée pas systématiquement toutes les tables dès le premier commit. » Chaque table différée a un lot prévu (DEVELOPMENT_PLAN). | `capacity_offers.provider_user_id` pointe un utilisateur ; une `organization_id` nullable sera ajoutée au lot 2. |
| D-006 | **Réconciliation du workflow du prompt** (`DRAFT→REQUESTED→BOOKED→ACCEPTED→HANDED_OVER→…`) : DRAFT/REQUESTED = états de la **demande** (`open/booked/cancelled`) ; BOOKED = états de la **réservation** (`requested/accepted/rejected/cancelled/superseded`) ; le **colis** naît à l'acceptation, son premier état est `ACCEPTED`. États d'exception : `CANCELLED, DELIVERY_FAILED, DAMAGED, LOST, DISPUTED, RETURNED`. | Le prompt demande « créer un colis associé à la réservation » *après* acceptation : une seule table ne peut pas porter les trois cycles de vie. | Table de transitions déclarative + rôles dans `src/domain/workflow.ts`, testée exhaustivement. |
| D-007 | **Périmètre géographique configurable** : `src/config/cities.ts` (villes + couloirs orientés), synchronisé en base par `db:migrate` ; un couloir retiré est **désactivé**, jamais supprimé. Couloir de validation : Dakar ↔ Abidjan. | Prompt §5. Ces entrées n'attestent aucun service de transport. | Ajouter un couloir = éditer le fichier + relancer la migration. |
| D-008 | **Montants en entiers mineurs, poids en grammes**, devise portée par chaque offre (XOF, XAF, EUR, CAD, USD), arrondi demi-supérieur, **aucune conversion de devises**. Contrainte SQL `net + commission = sous-total`. Commission en points de base, **0 par défaut** (`PLATFORM_FEE_BPS`). | Le PDF montre des annonces en EUR **et** en FCFA, au kilo **et** au forfait. Pas de flottants pour l'argent. | Tarif au forfait/paliers : non couvert (NEXT_STEPS). Le taux 5 %+5 % de GP Delivery est une observation de benchmark, pas une décision. |
| D-009 | **Politique de marchandises interne, NON validée juridiquement** : `allowed / review / prohibited` (`src/config/goods-policy.ts`). Un transporteur doit **opter explicitement** pour chaque catégorie ; les catégories `prohibited` sont refusées partout ; `review` génère un avertissement et un drapeau. | Prompt §14 : ne pas fabriquer de règles douanières. Les catégories s'inspirent des « tarifs spéciaux » vus dans le PDF. | **À valider par un professionnel** avant tout usage réel. Affichée sur `/about` et dans l'API (`validatedLegally: false`). |
| D-010 | **Matching déterministe** : filtres obligatoires (trajet, statut, dates, dernier dépôt, capacité poids/volume, catégorie, fournisseur actif, pas sa propre offre) → exclusion avec raisons ; puis score 0–100 sur 5 critères (prix 35, proximité de date 20, fiabilité 20, délai 15, marge de capacité 10). **Hypothèses non calibrées**, configurables (`ALX_MATCHING_WEIGHTS`), détail exposé. Budget et échéance sont *souples* sauf case « strict ». Information absente ≠ exclusion : drapeau visible (« arrivée non déclarée »). Fiabilité = lissage de Laplace (0,5 sans historique). | Prompt §11. | L'identité vérifiée est **affichée**, pas notée. Pas de ML. |
| D-011 | **Dates en GMT** (saisie et affichage), signalées dans l'UI. | Dakar et Abidjan sont toutes deux en UTC+0 toute l'année. | À remplacer par un fuseau par ville dès qu'un autre couloir s'ouvre. |
| D-012 | **Code de remise** : 6 chiffres, généré **par l'expéditeur** (jamais visible du transporteur, affiché une seule fois), stocké en HMAC-SHA256 (secret serveur + id colis), **5 tentatives**, expiration **30 jours**, usage unique, ≤ 5 régénérations (qui invalident l'ancien et remettent les tentatives à zéro). Les tentatives ratées sont enregistrées même si la requête échoue. | Prompt §13 ; pratique observée chez GP Delivery et Kifurushi (code unique à 6 chiffres). Le transporteur ne doit pas pouvoir se confirmer lui-même. | `DELIVERED` n'est atteignable que via `confirm-delivery` (ou résolution de litige par un opérateur). Le code reste faible face à une attaque hors-ligne sans secret : d'où le pepper obligatoire en production. |
| D-013 | **Capacité réservée à l'acceptation**, pas à la demande ; plusieurs demandes en attente possibles. Anti-surréservation : verrous de lignes `FOR UPDATE` dans l'ordre **demande → offre → réservation → colis**, index uniques partiels (une réservation active par paire demande/offre ; une seule acceptée par demande), contraintes CHECK de capacité. L'acceptation supplante les autres demandes de la même demande. | Prompt §18 (doubles réservations). Test de mutation : sans les verrous, 3 tests de concurrence échouent (10 acceptations pour 3 places). | L'annulation d'un colis `ACCEPTED` libère la capacité et rouvre la demande. |
| D-014 | **Données démo isolées** : colonne `is_demo`, e-mails `@demo.alx.invalid`, seed **uniquement manuel** (`db:seed:demo`, refusé en production), jeu de données **exclusif** (recherche réelle OU démo, réservation démo↔réel refusée), badge « DÉMO » partout. Aucune donnée dans les migrations (test automatisé). | Prompt §5, §17. | `db:reset:demo` supprime les lignes démo (désactive brièvement les triggers d'immutabilité, uniquement pour elles). |
| D-015 | **Aucun paiement**. Pas de table `payments`, pas de clé, pas de webhook. Le règlement est hors plateforme ; pas de « séquestre ». | Prompt §14. Un séquestre exige un prestataire agréé et une validation juridique. | Documenté dans l'UI, l'API et `/about`. |
| D-016 | **API v1 documentée et vérifiée** : `docs/openapi.json` est **généré depuis les schémas zod** réels ; un test échoue si le fichier est périmé ou si une route n'est pas documentée. Réponses `{data}` / `{error:{code,message,details}}`. | Éviter la dérive documentation/code. | `npm run docs:openapi`. |
| D-017 | **Identité : déclaré ≠ vérifié ≠ décision opérateur**. Aucun fichier ni numéro de pièce n'est stocké ; « verified » exige un relecteur (contrainte SQL) et une trace d'audit ; on ne peut pas se valider soi-même ; un nom vérifié est verrouillé. | Prompt §13. | La vérification elle-même est hors plateforme. |
| D-018 | **Journaux append-only** (`shipment_events`, `audit_logs`) protégés par triggers PostgreSQL ; l'audit refuse les clés évoquant un secret. | Intégrité de l'historique et des preuves. | — |

Le problème n'est pas simplement :

Elles disposent de :

* camions ;
* vols/groupages ;
* entrepôts ;

### B. Voyageurs

Un voyageur possède parfois :

> « Paris → Dakar le 20 août, 20 kg disponibles, contactez-moi WhatsApp. »

### C. Chauffeurs

Un chauffeur fait :

> Dakar → Thiès → Touba

avec éventuellement de l'espace disponible.

Mais il ne connaît pas forcément quelqu'un ayant un colis à transporter.

* Facebook ;

### Les quatre fonctions fondamentales

**1. Find : trouver une solution d'expédition.**

Un client saisit son trajet, son colis, son budget et son délai.

**2. Match : trouver le prestataire adapté.**

Le système compare les capacités disponibles, les prix, les délais et la fiabilité.

**3. Move : organiser le transport.**

La plateforme coordonne la prise en charge, les étapes de transit et la livraison.

**4. Trust : sécuriser les échanges.**

Elle organise la vérification des acteurs, la traçabilité, la preuve de remise, les paiements et les réclamations.

Cette organisation doit guider toute l'architecture logicielle.

## 2. Les quatre marchés à réunir

Il faut distinguer quatre mécanismes commerciaux, car ils ne nécessitent pas exactement les mêmes fonctionnalités.

### Marché A — Le transport entre particuliers

Un voyageur publie :

* son origine et sa destination ;
* sa date de départ ;
* sa date d'arrivée estimée ;
* son poids disponible ;
* son volume disponible ;
* son prix au kilogramme ;
* les catégories de colis acceptées.

Un expéditeur recherche un trajet et réserve de la capacité.

### Marché B — Le transport professionnel

Une agence publie ses trajets, ses tarifs et sa capacité disponible.

Elle peut recevoir des demandes de particuliers ou d'entreprises.

### Marché C — L'appel d'offres logistique

Un client publie une demande d'expédition.

Plusieurs transporteurs peuvent proposer une solution.

La plateforme compare leurs offres et laisse le client choisir.

### Marché D — Le transport multi-segments

Un colis peut emprunter plusieurs moyens de transport.

Par exemple :

Dakar → Abidjan → Douala.

Chaque segment peut être assuré par un prestataire différent.

Cette dernière fonctionnalité constitue une évolution importante, mais elle ne doit pas être indispensable au premier prototype.

Ces informations doivent venir des prestataires ou de sources opérationnelles appropriées.

**Décision recommandée :** utiliser OpenRouteService pour les calculs géographiques compatibles, sans lui confier la totalité du moteur logistique.

# PARTIE VII — Construire le produit sans surdimensionner le MVP

## 19. Architecture initiale recommandée

Pour un prototype développé avec Claude Code, je privilégierais un **monolithe modulaire**, et non des dizaines de microservices.

Pourquoi ?

* moins de configuration ;
* moins de déploiements ;
* moins de contrats interservices ;
* moins de complexité pour les tests ;
* moins de coûts ;
* moins de contexte à fournir à Claude Code.

### Stack possible

| Couche | Choix de départ |
| --- | --- |
| Frontend | Next.js, React, TypeScript |
| UI | Tailwind CSS et composants accessibles |
| Backend | API TypeScript dans le même projet ou service Python séparé si nécessaire |
| Base de données | PostgreSQL |
| Authentification | Solution adaptée au modèle retenu, par exemple Supabase Auth |
| Stockage | Stockage objet compatible S3 |
| Cartographie | MapLibre ou Leaflet |
| Géocodage/routage | OpenRouteService ou solution compatible |
| Tests | Tests unitaires, intégration et parcours essentiels |
| Déploiement | Docker et environnement simple |
| Documentation API | OpenAPI |

Je laisserais Claude vérifier si un backend séparé est réellement nécessaire avant de choisir entre une architecture TypeScript unifiée et un service Python.

**Il ne faut pas adopter deux langages côté serveur uniquement parce que nous voulons utiliser quelques fonctions d'IA.**

## 20. Le modèle de données minimal

Les entités fondamentales seront :

```
User
Organization
OrganizationMember
CarrierProfile
TravelerProfile
DriverProfile
RelayPoint
Route
RouteSegment
CapacityOffer
ShipmentRequest
Shipment
ShipmentItem
Booking
Quote

Payment
Payout
Refund
Dispute
Review
Notification
ComplianceRule

```

Quelques précisions :

* Route représente un trajet ou une liaison.
* CapacityOffer représente une capacité commercialisée.
* ShipmentRequest représente le besoin d'expédition.
* Booking représente la réservation d'une capacité.
* ShipmentEvent représente une étape de suivi.
* Payment représente une opération financière.
* Payout représente le règlement d'un prestataire.

Il faut séparer ces concepts.

Une demande de transport n'est pas un colis.

Un colis n'est pas une réservation.

Une réservation n'est pas un paiement.

Et un paiement n'est pas une preuve de livraison.

Cette séparation rendra l'évolution du système beaucoup plus facile.

# PARTIE XI — Les trois décisions stratégiques à ne pas négliger

## 26. Ne confonds pas une liste de fonctionnalités avec un produit opérationnel

Un MVP peut posséder une belle interface et de nombreuses pages sans résoudre un seul problème réel.

La bonne mesure est le nombre de parcours complets qui fonctionnent.

Pour la première version, je privilégierais :

1. Publier une capacité.
2. Trouver cette capacité.
3. Réserver.
4. Transporter.
5. Confirmer la remise.

Le reste vient ensuite.

## 27. Ne construis pas ton propre système de paiement réglementé

Commence avec un prestataire existant qui peut légalement prendre en charge les flux nécessaires.

Tu pourras développer ton propre module de facturation et de rapprochement, mais cela ne signifie pas que tu dois devenir toi-même un opérateur de paiement.

La distinction est particulièrement importante lorsque tu dois verser des revenus à des voyageurs ou à des agences dans plusieurs pays.

## 28. Ne commence pas par l'intelligence artificielle

L'IA ne compensera pas l'absence de données fiables sur :

* les routes ;
* les prix ;
* les capacités ;
* les délais ;
* les transporteurs ;
* les incidents.

Commence par enregistrer correctement les événements et les résultats.

Tu pourras ensuite utiliser ces données pour classer les offres, prévoir les délais, détecter les anomalies et améliorer le matching.
